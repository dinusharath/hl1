Design Document · Healthtech-1 Take-Home

Resilient form
ingestion, by design.

A system that takes registration forms from an unreliable provider — duplicates, silent schema changes, the works — and processes them so that nothing is ever lost, nothing is sent twice, and the on-call engineer sleeps through the night.

TypeScript PostgreSQL Prisma Docker Zod Jest
Author  Candidate submission Pattern  Inbox → State machine → Outbox Guarantee  Exactly-once egress

For non-engineers — what this guarantees, in plain terms

Every registration form that arrives is saved straight away, so none is ever lost — even if the provider sends it twice or sends it while the system is busy. Each form is processed once and only once, so a patient's details are never passed on twice. If the provider quietly renames a field or sends an answer we don't recognise, the form is safely set aside instead of dropped, and a person is asked to decide in the Drift Console. Fixing that kind of change takes a single approval in that console — no code changes and no deployments. The system recovers from everyday hiccups by itself and only asks for a human when there is a genuine ambiguity.

01
The real brief

What is actually being graded

The functional endpoint is the easy 20%. The remaining 80% is a resilience story: the provider is explicitly described as untrustworthy, and the three sample forms are deliberate edge-case landmines. The design below is organised around the hard guarantees, not the CRUD.

Idempotency

The provider doesn't promise exactly-once delivery. Duplicates must collapse to a single processed form.

Exactly-once egress

FORM-BOT must never receive the same form twice — enforced at the database, not in app logic.

Schema tolerance

Unannounced schema changes must never cause a form to be rejected or dropped.

Self-recovery

Flaky downstreams (~5% failure) recover automatically. A human is paged only as a last resort.

03
Per-form lifecycle

A state machine you can crash

Each form carries a status. Every transition is idempotent and committed before the next begins, so an interrupted form always resumes from where it stopped — never from the start, and never skipping ahead.

PENDING PROCESSING TRANSFORMED GEOCODED DISPATCHED DONE
data problem (ambiguous / unresolved drift) → NEEDS_REVIEW human decides → replay
our problem (deterministic bug / unexpected throw) → FAILED fix code → replay

PROCESSING is a worker lease (claimed via FOR UPDATE SKIP LOCKED + claimed_at) — two workers never grab one form, and a worker that dies mid-flight has its row reclaimed after the lease expires. The two dead-letter states are deliberately split by owner: NEEDS_REVIEW for a human data decision, FAILED for a code fix — both replayable, neither a crash or a dropped form.

05
Delivery semantics

Two destinations, two guarantees

Honesty about semantics is itself a design decision — and a strong talking point.

There is no transactional exactly-once to an external system. You can't atomically commit a DB row and an HTTP side-effect — the dual-write problem. So we build it from two honest halves instead of claiming magic.

Effective exactly-once

FORM-BOT

One work item: outbox UNIQUE(form_id, 'FORMBOT') — no duplicate intent. One effect: we send a stable idempotency_key; FORM-BOT (ours, "never crashes") returns a deterministic ack — accepted vs already-have-it. We mark DELIVERED only on ack; a row stuck in SENDING is re-driven by a reconciliation sweep — safe to resend because the key dedupes it.

At-least-once

Confirmation email

Enqueued the moment transform succeeds — independent of the FORM-BOT outcome (the brief gates it on transform, not delivery). Retried with a high cap until it lands. Email has no dedupe handle, so at-least-once is the truthful promise: a duplicate confirmation is harmless; a missing one is not.

Independent retries. The two outbox rows are dispatched on their own schedules, so a stuck FORM-BOT never blocks the guaranteed email — and vice-versa.

How do we know it's "the same" one?

Sameness is declared, not guessed: session_id is the key the provider replays on redelivery. But a reused id carrying different data must not be silently dropped — so we also store a payload_hash and split the conflict three ways.

Same session_id?Same payload_hash?Verdict
no—New form → process normally
yesyesTrue duplicate → bump duplicate_count, no reprocess, 202
yesnoAmbiguous — reused id, changed data → NEEDS_REVIEW + ingest.conflict, never dropped

The assumption, stated. This rests on the provider reusing session_id on resend. The brief says it's badly behaved — so payload_hash is the safety net: it still catches byte-identical replays even if that assumption breaks.

Defence in depth. session_id dedupes at the front door; the outbox UNIQUE(form_id, type) is a second, independent lock so FORM-BOT stays exactly-once even if a duplicate ever slips past ingest.

08
Failure handling

Recovery, and how it's proven

We own the retries

After the 202, every downstream retry is ours — exponential backoff + jitter, persisted attempts/next_attempt_at. The provider only re-drives a failed ingest.

Multi-worker safe

Claim via FOR UPDATE SKIP LOCKED + claimed_at lease. No double-grab; a dead worker's row is reclaimed after the lease. Each reclaim bumps attempts.

Poison-message safe

Each form runs in its own try/catch — a throw bumps attempts and releases the row; it never crashes the loop or spins forever.

Deterministic tests

Mock failure rates are injectable (not Math.random()), so resilience is asserted, not hoped for.

Error taxonomy — retry vs fail fast

Not every failure deserves a retry. Classifying them is what keeps the review queue honest and stops a bug from silently burning the retry budget.

ClassExamplesAction
Transientdownstream 5xx · timeout · DB deadlockbackoff + retry; cap → NEEDS_REVIEW
Permanentour bug · 4xx · un-parseable data · unexpected throwno retry → FAILED fast, keep the stack

09
Self-healing drift

Turn a 3am page into a one-click fix

The baseline never drops a drifted form — but a recurring schema change shouldn't stay a standing incident. This layer records every mismatch, groups it, and hands on-call a suggested mapping to approve — including an N→1 composite suggestion when a provider splits one field into several (firstName+lastName instead of name), which a 1→1 rename would otherwise answer by silently dropping the second field. Approving writes a versioned DB mapping (hot-reloaded, no deploy) and replays the blocked forms. When nothing scores confidently, the operator is never stuck: they map the form's real fields by hand, save-or-skip.

Guardrails. Nothing acts without an approved suggestion except the two curated built-in composites (firstName+lastName → name, and the snake_case equivalent) — a composite otherwise never auto-applies, since join-vs-alternatives can't be settled from field names alone. Mappings are versioned & reversible (roll back = deactivate + re-replay); no PII leaves the trust boundary for drift observations (redacted shapes/exemplars only — the one deliberate exception is the operator-only hand-mapping and conflict-resolution views, which show the real payload because an authorized human reconciling a specific stuck form needs to see it); replay is idempotent.

Built, not a mockup: the review/approve flow, hand-mapping, and conflict resolution all run in a real operator console (../healthtech-ingestion-ui), wired to the live API — every action it takes is a plain endpoint listed in /docs. Scope & honesty

What's in, and what I'd do next

In scope now

Durable ingest, dedupe, transform, geocode-with-retry, outbox dispatch, both delivery guarantees, schema tolerance, and the three test layers — plus a working operator console wired to all of it: drift review + approve/dismiss, the mapping registry (including N→1 composite rules), dead-letter replay, hand-mapping a stuck form with no confident suggestion, and resolving a same-session payload conflict without ever dropping the disputed data.

With more time

The LLM (Claude) fallback for drift suggestions the rule engine scores low — the one genuinely unbuilt piece of §9 — plus BullMQ for higher throughput, PII-at-rest encryption, a richer per-form timeline trace, and a real geocoding provider.

PHI note. This is healthcare data — payloads are never logged in full, secrets come from env (.env.example provided), and at-rest/TLS handling is called out as considered-but-out-of-scope for the exercise.
